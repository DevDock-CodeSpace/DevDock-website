# Issues, Plans and the Issues hub

Read before touching `features/issues/`, `features/plans/` or the hub routes.

- **Plans and the Issues hub** (`features/plans/`, `features/issues/hub/`, routes under `/t/:teamSlug/issues`; `docs/ISSUES_HUB_PLAN.md` has the owner's decisions):
  - **A plan is Linear's "project"**: a goal assigned to issues like a label (`issues.plan_id`, at most one), with a page (name, description as TipTap JSON edited as plain text for now, status, lead, start/target dates, progress from its issues). Issues still **live in a project** (number, labels, sprints); plans have no labels or sprints of their own and can hold issues from several projects. `plans` is group-level: everyone in the group reads them and **anyone creates one** (the creator leads it); its lead, its creator and group owners/admins edit and delete (RLS); `check_plan` keeps the lead in the group; `check_issue_plan` keeps an issue's plan in its group; plan changes are activity kind `plan`. In the realtime publication (`AFFECTS.plans`, live root `plans`). `teamPlansQuery` (one request, the whole group) feeds pickers, chips, the hub and the issue context (`useIssueContext().plans`, prefetched by `issuesLoader`).
  - **Plan files** (owner's choices, 2026-10-27): every plan has a folder in Files, **Plans / <plan name>** (group-wide; `doc_folders.plan_id`, the group's `is_plans_root` folder), made with the plan by a trigger (`private.ensure_plan_files`), holding a **Brief** doc (the plan's description: the plan page previews it, `plans.brief_id`; `planQuery` embeds its text) and a **Whiteboard** (`plans.whiteboard_id`; New plan = `rpc('create_plan')` makes it at once, imported plans get it on first open, `rpc('plan_whiteboard')`). **Everyone in the group edits plan files**, whiteboards and doc images included (`private.plan_of_folder` in the diagram policies and `can_access_doc_image`); deleting a single file stays with writers. Plan folders follow their plan: renamed with it (trigger), never renamed, moved, shared or deleted by hand (`protect_plan_folders`, SQLSTATE `DD002`; Files hides their menu, drag and checkbox). **Deleting a plan deletes its folder and files** (`deletePlan`: the docs' images first, then `rpc('delete_plan')`; the warning counts them with `rpc('plan_files')`); its issues stay, without a plan.
  - **Plan rules on issues** (owner's choices, 2026-10-27; `20261027100000_plan_filter_and_sub_issue_plans.sql`): a project's Issues page filters by **plan** (facet `plan` in `filters.ts`, ids or `none`; saved views may keep it, `prepare_issue_view` allows it). A **sub-issue is always in its parent's plan**: `sub_issue_takes_plan` sets it on insert or a new parent, `sub_issues_follow_plan` carries a parent's change down every level; the issue page, list chips and New sub-issue show it read-only ("from parent").
  - **Look (Graphite, owner's choice 2026-10-27, in DevDock's own frame):** the hub has its own header ("Issues", ⚙, the tab's one main button) and underlined icon tabs with counts (My issues: your open ones in view; Plans: all); toolbars use `Segmented` (`features/issues/hub/components/Segmented.tsx`) and quiet selects. Plans is a table grouped by status (status tile `planStatusTile`, the Brief's first words, lead, target in amber within 7 days and red when late, done/total, `ProgressRing`); the first words come with the list from the computed column `public.brief_excerpt(plans)` (160 chars, no extra request; not in the generated types, so `teamPlansQuery` casts with `.returns<Plan[]>()`). Breadcrumbs on the hub are Issues › tab › plan (`useItemCrumb`).
  - The plan page (`PlanPage`, no hub tabs above it): a status tile, the name (editable by lead, creator and admins) and a one-line summary; ★, New issue, ··· (open its folder, delete). Main column: the plan's files as a **horizontal 3D stack** (`FileStack`: the Brief first with 4 lines of it, the Whiteboard or "Start the whiteboard", then the folder's other files; plain CSS transforms, no library; ‹ ›, dots, ← → when focused and a sideways trackpad swipe move it, a vertical wheel stays the page's; New doc or whiteboard goes into its folder), Up for grabs (one note for projects you're not in), then its issues by person. Right: a **details panel** (big ring, status bar by issue status, status/lead/start/target editable, people, projects) with ✕; it **starts open and isn't remembered** (owner's choice). Everything comes from cached lists plus `planLoader`'s requests (opening a plan: plans, documents, diagrams in parallel).
  - On issues: **Plan** row on the issue page, plan chip on rows (`IssueRowSource.plans`), Plan chip in New issue. `?new=1` / `?new=<plan id>` on a project's Issues page opens New issue (in that plan): how the hub and a plan's page create issues in a project (`NEW_PARAM`).
  - **The hub** (`IssuesHubLayout`; `issuesHubLoader` starts the group's issues, plans and people side by side; every tab is lazy): **My issues** (default; only what's assigned to you, Open / Done / All, project and plan filters; owner's rule "your own work first": there is no All issues tab, others' work is seen in a plan, a sprint or a view), **Plans** (`HubPlansPage`), a plan (`PlanPage`, `planLoader`: details, **Up for grabs** = its unassigned open issues with **Assign to me** where you're in the issue's project (`useHubProjects().canTake` mirrors `has_workspace_access`), then its issues by person), **Sprints** (`HubSprintsPage`, `hubSprintsLoader`: each project's running or next sprint, issues by person; sprints are set up on the project's Sprints page; `projectsCyclesQuery` = every project's sprints in one request), **Views** (`HubViewsPage`, `hubViewsLoader`). Header: one main action per tab (owner's choice, 2026-10-27): **New plan** on Plans (the list and a plan's page), **New issue** on every other tab (`ProjectChooser` goes straight to the project when there's one, else asks which), and a ⚙ link to **Issue settings** (`HubSettingsPage`, `hubSettingsLoader`; leads and admins): per project you manage, Import issues and **People from imports** (`ImportPeopleList`, shared with project Settings → Import). Importing happens every few months, so it isn't a header button (owner's choice, 2026-10-27).
  - Import maps Linear's **Project → plan** (an existing plan with the same name, ignoring case, is reused; `import_issues` `p_plans`), Milestone → label. Import is reached from the hub's Issue settings (`…/settings/import?from=hub`, back link to Issue settings) or project Settings → Import.
- **Issues** (`features/issues/`, routes `…/w/:id/issues` (`?view=board`) and `…/issues/:issueNumber`, `issueLoader`):
  - **Loading:** the `issues` route has a loader (`issuesLoader`) that prefetches members, labels, sprints, repos, saved views and (except on a single issue's page) the issue list in parallel, and `useIssueContext` reads its four queries as one batch. Keep new Issues-page data in that loader so the page never loads it one request at a time.
  - Rows are addressed by **number within the workspace**, not UUID. The identifier is `issueIdentifier(workspace.issue_key, number)`.
  - `number`, `team_id` and `created_by` are set by DB triggers (`private.issue_counters`). The assignee-is-a-member, same-workspace-parent and no-loop rules are enforced by the `check_issue` trigger.
  - Labels on an issue are replaced with `rpc('set_issue_labels')`.
  - **Images in descriptions** (`images.ts`): the docs `docImage` node, stored in the same `doc-images` bucket under `issues/<workspace_id>/<file>` (Storage RLS: workspace viewers view and upload; the uploader or a manager deletes). The issue page uploads on paste/drop/pick; the New issue dialog keeps picked files locally and uploads them on Create, appended after the text. `deleteIssue` removes the description's images.
  - Field edits go through `useUpdateIssue()` (optimistic, rolls back with a toast). Pickers use the searchable `Picker` popover.
  - The issue page's title and description save themselves (`hooks/use-save-on-exit.ts`): while typing, on leaving the issue, and when the tab is hidden or closed. `useUpdateIssue` runs saves one at a time (mutation `scope`); `IssueDescription` queues its own saves, writes the cache when a save starts, and takes a changed server description only when nothing is unsaved.
  - `useIssueContext().canManage` mirrors `private.can_manage_workspace` (UI only).
  - Cycles live under `…/issues/cycles[/:cycleNumber]` (`cycleLoader`). Numbering and the no-overlap rule are enforced by the `prepare_issue_cycle` trigger; `rpc('move_open_issues')` rolls open issues over.
  - `issue_activity` is written only by triggers (`log_issue_activity`, `log_issue_label_activity`); clients can only read it. Don't add client-side activity writes.
  - **Nested list** (`NestToggle`, `useNested`, localStorage `devdock-issue-nested`, one choice for every issue page; List only): sub-issues sit under their parent, closed until its arrow is clicked (open state is per visit), indented per level; a sub-issue whose parent is filtered out stays in its own status group. Built from the list already loaded (`parent_id`), so it costs no request; J/K follow the rows on screen.
  - **Import** (`features/issues/import/`, route `…/w/:id/settings/import`, lazy `IssueImportPage` under `WorkspaceToolGate tool="issues"`, `issueImportLoader`; reached from project **Settings → Import** (`ImportSettingsSection`, owner's choice 2026-10-26: not on the Issues page), which also lists **who each imported name is mapped to** (`issue_import_people`, `rpc('import_people')` with how many issues still wait; changing a person runs `map_import_assignee`, which records the mapping and assigns the waiting issues; later imports start from these mappings; `workspaceSettingsLoader` prefetches it with the labels and people; in `NOT_LIVE`, the table isn't published)): leads and group owners/admins only (`import_issues` checks `can_manage_workspace`). Pick a source (CSV / Linear / Notion / Jira; only changes the how-to and how descriptions are read; a Linear or Jira file is recognised by its headers), drop the file (≤ 5 MB, ≤ 1000 issues), then one page: **Columns** (`guessMapping`, header names per field in `fields.ts`; Jira's repeated Labels/Sprint columns are read together), **Values** (each status, priority, person and sprint in the file → a DevDock one; unmatched ones are marked; people match by display name, an email's name part, or a unique first name, because emails aren't readable; anyone unmatched is **kept by name** by default: `issues.import_assignee` holds the file's name or email (owner's choice, 2026-10-26) until a lead maps it in Settings → Import (one request assigns all their issues; `import_issues` also records every name in the file with whoever it was matched to, `p_people`; assigning the issue any other way clears it, `clear_import_assignee` trigger); rows and the properties panel show the kept name; a sprint the file describes with dates (Linear's Cycle Name/Start/End, `sprintsInFile`) is **created** by default, keeping the file's number when it's free (`devdock.cycle_number`, read by `prepare_issue_cycle`), ending the day before Linear's end (Linear's end is the next cycle's start; DevDock's may not overlap), and skipped if it overlaps a sprint already there; Linear's **Project** becomes a **plan** and its **Milestone** a label, cut at a word to 40 characters (`labelName`)), **Preview** (exactly what will be sent; `buildImport` orders parents before sub-issues and breaks loops). Everything is computed in the browser from the Issues loader's cache, so the page makes **no request until Import, which is one**: `rpc('import_issues')` (security invoker, so RLS, column grants and every issue trigger apply per row; all rows or none; missing labels created). Each imported issue keeps `import_source` + `import_ref` (the file's ID, or `title:<title>` when there is none; unique per workspace), so importing the same file again skips what's there and sub-issues can join a parent imported earlier. Descriptions: Markdown (Linear, Notion) through `@tiptap/markdown` in `markdown.ts` with the editor's node names but without lowlight; images become links and tables code blocks, headings deeper than H3 become H3, and anything the schema refuses, or Jira's wiki markup, is kept as plain text. The page uses plain selects, not the issue pickers: the pickers in this chunk made Rolldown split first-load code into extra chunks (+3.5 KB). `csv.ts`, `fields.ts`, `values.ts` and `build.ts` import nothing from `@/` so Deno tests run them (`npm run test:import`); keep it that way. Not built (owner declined for now): original created/completed dates, the original creator, links between issues; also comments and attachments.
  - Views are URL state: `?tab=`, filter facets (`readFilters`/`writeFilters`, `useIssueFilters`, which reads the URL directly and composes quick successive changes), `?view=board`.
  - **Saved views** (`issue_views`, `views.ts`/`viewsApi.ts`/`viewsHooks.ts`, components `ViewsMenu`/`OpenViewTab`/`ViewActions`/`ViewDialog`): opening one copies its state into the URL (`viewHref`, `?v=<id>&tab=…&status=…`), so the URL stays the single source of truth; "modified" is the URL differing from the saved state (`sameViewState`), and Save changes / Reset / Save as new act on that. A bare `?v=` link is filled in once (`useActiveView`). Visible to the owner, or to the workspace when `shared`; owners edit them, and workspace managers can edit or delete shared ones but cannot make someone else's view private (RLS). Names are unique per owner, at most 50 per person and workspace; `filters` is validated by `private.prepare_issue_view` (only the known facets, lists of short strings). Choosing a built-in tab leaves the view and starts fresh.
  - **Cycle insights** (`cycleStats.ts`, `CycleInsights`, `BurnupChart`, `BreakdownPanel`, `SidePanel`): a details panel beside the list on the cycle page (and on the issues list, as `ViewInsights`, with a saved view's visibility and owner), toggled with the panel button (`usePanelOpen`: **always closed when a page opens and never remembered**, owner's choice 2026-10-27: the list comes first). For a cycle it shows scope / started (in progress or review) / completed, a burn-up chart, and Assignees / Labels / Priority breakdowns with completion rings; Issues or Hours when estimates exist. The chart is rebuilt from `issue_activity` (`cycleHistoryQuery`: when each issue entered or left the cycle and when its status changed), so work added or removed mid-cycle shows as scope changes; canceled issues are never in scope. `cycleSeries` is pure and tested.
  - **Cycle pins:** a specific cycle (`kind='cycle'`, `cycle_id`) or "Current cycle" (`kind='current_cycle'`, no target; it points at `…/issues/cycles/current`, which resolves to whichever cycle is running). `CyclePinButton` offers both on the running cycle. Deleting a cycle removes its pins.
  - **Starred** (the UI word since 2026-10-27, owner's choice, so it isn't Linear's "Favorites"; code keeps `issue_pins`, `usePins`, `PinButton`, `CyclePinButton`, `PinnedNav`; one amber ☆ everywhere, `StarButton` for issues, plans and My issues; the list is titled **Starred** and sits **under the group's Settings, set apart by a wide gap** (moved up from the sidebar's bottom on 2026-10-27)): kind `view` / `person` / `tab` / `cycle` / `current_cycle` (a project's, from its Issues page), `workspace` (from the sidebar or the workspace list) or `issue` / `plan` / `my_issues` (`plan` and `my_issues` have no workspace, `issue` takes its issue's), per person and group, ordered by `position` (`reorder_issue_pins`; at most 30 of every kind together). Starring and unstarring are optimistic (`usePins`): a new star gets its id in the browser (`grant insert (id)`, `20261027080000_star_client_ids.sql`), and star and unstar share a mutation `scope`, so unstarring something starred a moment ago runs after the insert and deletes it (it used to be skipped silently). `PinButton` stars what's on screen: the open view, a person-only filter (`personOf`), or a plain tab; unsaved filters can't be starred. A view star must point at a view you can see, a person star at someone in the group. `PinnedNav` hides stars whose view or project you can't reach (or that are outside the collection view) and shows the project name only when the group has several. This is the one deliberate exception to "workspace features aren't sidebar items".
  - Shortcuts use `useShortcuts` (ignored while typing or while a menu/dialog is open). Lists get J/K focus and per-row menus through `IssueCollection` + `IssueNavContext`.
