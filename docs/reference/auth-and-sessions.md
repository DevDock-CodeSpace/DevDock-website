# Sign-in, sessions and inactivity

Details behind the auth rules in CLAUDE.md. Read before touching `features/auth/`, `lib/auth-storage.ts` or `lib/inactivity*`.

- **Supabase Auth with Google** for everyone, plus **one email + password admin account** the owner asked for so the app can be opened without a Google round trip (testing, automated request counts): `/admin-login` (`AdminLoginPage`, `signInWithPassword`, linked from nowhere). The account is created in the Supabase dashboard (Authentication → Users), never in code, and its password is never committed. Since 2026-10-27 it is the **platform admin** (`super@admin.com`, see `docs/reference/platform-admin-and-flags.md`): it belongs to no group and opens the console at `/admin`. Other password accounts (demo people, `dev-admin@devdock.test`) have no special powers: what they see comes from their group and workspace roles under RLS. There is no sign-up or reset in the app. Enabling the Email provider means anyone can try passwords against the project's auth API, whatever the page URL; the owner accepted that. No magic links or other providers unless asked. PKCE flow (`flowType: 'pkce'` in `src/lib/supabase.ts`); `redirectTo` is always `window.location.origin + '/auth/callback'`, never a hardcoded host.
- **Where the session is kept, and for how long** (`lib/auth-storage.ts`, passed to `createClient` as `auth.storage`; `RememberMe` on `/login` and `/admin-login`): the owner asked for it. Browser only; Supabase's own session limits need the Pro plan, so refresh tokens stay valid on the server and the browser drops them.
  - Default: **sessionStorage**, so the session belongs to the tab (a new tab signs in on its own; closing the tab ends it). "Remember me" ticked: **localStorage**, shared by every tab and kept across restarts. The choice is `devdock:rememberMe` in localStorage, set **before** sign-in (the PKCE verifier is stored the same way) and kept as the box's default.
  - A session lasts **4 hours** from sign-in, **12 hours** when remembered (`devdock:signedInAt`, kept beside the session). `requireUser` and `InactivityGuard` (every 30 s, on focus) sign out with `/login?reason=expired`. Sign-ins start the clock (`startSessionClock` in `authCallbackLoader` and `signInWithPassword`); connecting Google Calendar doesn't. A session from before this existed starts its clock on first check.
  - Not remembered, nothing of the session is on disk: a token an older version left in localStorage is dropped. Cookies were considered and rejected: with no server of our own they'd be readable by JavaScript like localStorage, capped at 4 KB, and sent to Vercel on every request.
  - Tests: `npm run test:idle` (with the inactivity tests).
- **Inactivity sign-out** (`lib/inactivity.ts`, `lib/inactivity-config.ts`, `hooks/use-inactivity-logout.ts`, `InactivityGuard` on the `app` route): the owner asked for it because idle tabs kept making requests, and every request is a log line. Browser only: no server setting, table or request is involved.
  - Input means what a person does (`INPUT_EVENTS` in `use-inactivity-logout.ts`): pointer, keys, touch, wheel. Not `scroll` (the chat list scrolls itself to new messages, which kept idle Messages tabs signed in), not a `pointermove` whose position didn't change (browsers send those when the page changes under a resting cursor), and nothing the page dispatches itself (`isTrusted`).
  - 15 minutes without input in **any** DevDock tab (`VITE_INACTIVITY_LIMIT_MINUTES` overrides it) signs the browser out (`signOutForInactivity`, `scope: 'local'`) and opens `/login?reason=inactive&next=…`. A dialog asks first, 120 s before.
  - The decision is always `Date.now()` minus the last activity, kept in localStorage (`devdock:lastActivityAt`, one clock for all tabs, written at most every 5 s). Timers only ask the question again (every 30 s, on becoming visible, focus, `pageshow`, `online`, a `storage` event), because they stop while a laptop sleeps. Never replace this with one long `setTimeout`.
  - Sessions can be per tab, so another tab's sign-out doesn't reach this one: a tab that finds the clock cleared with the idle note (`devdock:signedOutForInactivity`) signs out too; cleared by a sign-out by hand, its countdown restarts from now.
  - Once the limit has passed nothing revives the session: the first mouse move after waking doesn't count, and a failed sign-out (offline) is retried by the next check.
  - `requireUser` checks the same clock, so opening the app after a long absence goes to login before any data loads. Signing in restarts the clock (`startActivityClock` in `authCallbackLoader` and `signInWithPassword`); a new way to sign in must call it or the old timestamp signs the person straight back out.
  - **A call counts as activity** (`holdActivity()` in `LiveCallProvider`): its frame is cross-origin, so no input reaches the page. Use `holdActivity()` for anything else a person watches without touching.
  - Live updates ask the clock before refetching after a reconnect (`refreshAfterGap` → `inactivityExpiredNow`), so a laptop waking in the night is signed out, not caught up. A tab hidden for 5 minutes stops listening altogether (`useRealtimeSync`) and, when looked at again, subscribes and refreshes what's on screen once (about 11 requests on Home). The Realtime client closes its socket about a minute after the last channel goes.
  - It is a convenience, not security: it runs in the person's browser. Supabase's own session limits need the Pro plan.
  - Tests: `npm run test:idle` (Deno, no browser; time is a number the test moves).

## The auth rules, full wording

- **All auth calls live in `src/features/auth/api.ts`.** Components use the hooks in `features/auth/hooks.ts` (`useAuth`, `useCurrentProfile`, `useUserIdentity`, `useSignInWithGoogle`, `useSignOut`) and never import `supabase` directly.
- **Route protection happens in loaders, not components.** Any new authenticated route goes *under* the `app` route, whose loader (`src/layouts/app-loader.ts`) calls `requireUser(request)` before anything else. Child loaders that need the user call `requireUser` again (it's cheap; loaders run in parallel). Don't add `useEffect`-style redirect guards.
- **Post-login destination:** `/login?next=` (validated by `safeNextPath`: same-site paths only). It's stored in sessionStorage across the Google round trip so the callback URL stays fixed.
- **Identity changes** (sign-in/out in another tab, expired session) are handled once, in `watchAuthIdentity` (router.tsx): clear the query cache, then `router.revalidate()`. Never call Supabase APIs inside an `onAuthStateChange` callback (deadlock risk; defer with `setTimeout`).
- **Profiles are created only by the DB trigger.** Don't add client-side profile inserts. If a profile is missing or fails to load, the UI falls back to Google metadata (`useUserIdentity`).
- **Route guards are UX, not security.** Every data rule must be enforced by RLS. Don't pass user IDs from the client as proof of anything.
- **Errors:** show friendly messages (`features/auth/errors.ts`), log the raw error with `console.error('[auth] …')`, and never render Supabase/Postgres error text.
- **Adding a deployed environment:** add `<origin>/auth/callback` to Supabase → Authentication → URL Configuration → Redirect URLs, and the origin to Google's Authorized JavaScript origins. The Google client secret lives only in the Supabase dashboard.
