# Groups, workspaces, access and navigation

Routes, access checks, the sidebar, who can see a workspace, collections, team tools vs workspace tabs, page layout. Read before touching routing, the sidebar, workspaces, collections or access.

- **Routes.**
  - Public: `/login`, `/admin-login` (the admin account's password sign-in; both lazy routes drawn by `AuthShell`: a showcase of the app on the left on wide screens, made of plain markup, and the sign-in column), `/auth/callback`, `/privacy` (privacy policy for Google's consent screen; keep it matching what the app stores).
  - Authenticated (under route id `app`):
    - `/admin` (lazy, `adminLoader`): the platform admin console; a 404 for everyone else. See Platform admin below.
    - `/app` redirects to the last-used team's **start** page (`/t/:teamSlug/start`, `teamStartLoader`), or, with none, to `/admin` for the platform admin and `/onboarding` for everyone else. The start route picks the page (`landingPath` in `features/teams/landing.ts`, owner's rule 2026-10-26): when the collection in view (else the group) is **learning**, the course you last opened, on its Learning tab, else the first course; otherwise, or with no course, **Chat**. Switching group or collection (`TeamSwitcher`), creating or joining a group and leaving one all go through it. It reads the shell's cached workspace list (`teamContentsQuery`), so it adds no request. There is no Home item in the sidebar (owner's choice, 2026-10-25): the workspace list at `/t/:teamSlug` is reached from the sidebar's section titles ("Projects · 5").
    - `/onboarding`
    - `/github/callback` (back from installing the GitHub App).
    - `/t/:teamSlug` (the team's workspaces), plus `members` and `settings`.
    - `/t/:teamSlug/w/:workspaceId` (overview), plus `members` and `settings`; every other feature tab is `:tab`, checked against the workspace type in `WorkspaceTabPage`.
  - `/` redirects to `/app`.
- **Access checks in loaders** (`features/teams/loaders.ts`): `teamLoader` 404s when the user isn't a team member; `workspaceLoader` 404s when the workspace isn't visible (RLS: not added, and not let in by its access setting) or belongs to another team.
- **Current context:** `useCurrentTeam()` and `useCurrentWorkspace()` (`features/teams/hooks.ts`) return the entity, the user's role, and `can`, a permissions object from `features/teams/permissions.ts` that mirrors RLS. **`can` is for showing and hiding UI only.** The Group members page explains the roles in plain words (`RoleGuide`, wording by group type); update it whenever permissions change. Every write is re-checked by RLS. Type labels and icons are in `teamTypes` and `workspaceTypes` in the same file.
- **Sidebar limits:** each type section shows at most 3 items (`pickSidebarItems`): the most recently opened (localStorage, `features/workspaces/recent.ts`), falling back to recently updated. Starring a workspace (☆ on hover, `useWorkspaceStars`) puts it in the Starred list instead of keeping it in its section (owner's choice, 2026-10-27; old pins were copied over by `20261027070000_starred_workspaces.sql`; the `workspace_pins` table is unused and can be dropped once no tab from before that deploy is open). The open workspace always shows. The section title ("Courses · N") links to Home `?type=`. Long names use `TruncatedText` (tooltip only when cut off).
- **Navigation:** the **sidebar is the hierarchy**: team switcher, Chat, the **team tools** (Docs, Diagrams, Live; `TEAM_TOOLS`), the team's workspaces grouped by **workspace** type (Courses, Projects, Workspaces; empty sections hidden; the group type decides which section comes first, the default for "+ New", and **which types are allowed**: `allowedWorkspaceTypes` (learning: course/project/space; development: project/space, **no courses**; general: all), enforced by `private.check_workspace_type`/`check_team_type`. The `general` type is labelled **Space** in the UI. A group-wide **Issues** item (the Issues hub, below) sits below Live for development groups and for any group with a project the caller can see (`hasTeamIssues`, `IssuesHubLayout`, `teamIssuesQuery`)), one "+ New", team Members and Settings. **Workspace features are horizontal tabs** under the workspace title (`WorkspaceLayout`), **generated from the workspace's enabled tools** (`workspace_modules`; `getWorkspaceTabs(teamSlug, id, modules)` in `features/teams/nav.ts`): Overview, then the tools in `MODULE_ORDER`, then Members. Workspace *type* only picks default tools (`defaultModules`, which mirrors `public.default_workspace_modules`). Create workspaces with `rpc('create_workspace')` and change tools with `rpc('set_workspace_modules')`; both are atomic and run under RLS. Don't put workspace features in the sidebar.
- **Who can see a workspace** (`workspaces.access`, `features/workspaces/access.ts`, `AccessSection`, `AccessSelect`):
  - `members` (default: only the people added), `collection` (plus everyone in its collection) or `group` (plus everyone in the group). People let in by the setting have **ordinary member rights**; leads are always explicit rows. Group owners and admins see everything, as before.
  - The one place it is decided is `private.workspace_role()`: with no row in `workspace_members` it returns `'member'` when the setting lets the caller in. Every policy, Storage rule and Edge Function goes through it or `can_view_workspace`, so new tables inherit it. To ask about *another* person use `private.has_workspace_access(workspace, user)` (the assignee check in `check_issue`, `live_session_invitees`, `set_live_session_rsvps`); never read `workspace_members` directly for that.
  - Clients cannot write `access` or `collection_id` (no column grants). Change them with `rpc('set_workspace_access')` and `rpc('set_workspace_collection')`, group owners/admins only (`can.canChangeAccess`), because opening a workspace also admits everyone who joins later. Create with `rpc('create_workspace_in')`; the older `create_workspace` keeps its arguments for open tabs.
  - `workspaceMembersQuery` returns **everyone in the workspace** in one call (`rpc('workspace_people')`), each with `via`: `'member'` (added by name) or the setting that lets them in. Assignee pickers, class progress and the header use it as is; filter on `via === 'member'` when only explicit rows are meant (`AddWorkspaceMembersDialog`, the Members page's first list).
  - Nobody loses access silently: narrowing the setting asks first and names who is affected (group admins excluded, they keep it). Moving a workspace out of a collection it was open to, or deleting that collection, first gives the collection's people rows of their own (`private.keep_collection_people`) and falls back to `members`.
  - New-workspace default (`defaultAccess`): its collection when created inside one, the group for a course in a Learning group, otherwise only the people added. It is a visible choice in the dialog.
  - `supabase/tests/workspace_access.sql` is the re-runnable access check (one person per role against each setting; rolls back). Run it against the **local** database after touching any access helper.
- **Collections** (`workspace_collections`, `workspace_collection_members`, `features/collections/`; UI word "Collection"):
  - Optional, one level deep, never in a URL, invisible until one exists. Group owners/admins create them and choose their people in Group settings → Collections (`CollectionsSection`); people must be in the group and leave its collections when they leave it. Everyone in the group can read them (the member list is already group-wide).
  - A collection is a word for things, so where people are meant use its own name ("Everyone in Learning"), never "members of the collection".
  - They load **with the workspace list**: `teamWorkspacesQuery` and `teamCollectionsQuery` are two `select`s over one cache entry (`['workspaces', 'team', id]`, one request to `teams` with embeds). Read them with two `useSuspenseQuery` calls, not `useSuspenseQueries` (same key twice makes TanStack warn). A workspace's `memberCount` already includes whoever its setting lets in.
  - **One collection at a time** (`features/collections/view.ts`, `useCollectionView`): the owner asked that a group's collections never be shown together, because they are different parts and mixing them confuses people. The group menu (`TeamSwitcher`) opens a second menu on a group with collections; picking one sets the **collection view**, remembered per group in localStorage (never in the URL). `useCollectionView()` returns the `collection` in view (null in a group without collections, where nothing is narrowed), the group's `workspaces` narrowed to it, and `inView(workspaceId)`. The sidebar, Home, group-wide Issues, Docs, Diagrams, Meetings, pins and the create dialogs all read from it; use it instead of `teamWorkspacesQuery` in any new group-level list. Whether Issues shows, the section order and the "+ New" defaults follow the collection's type (`collectionTypeOrder`).
    - Group-wide rows (`workspace_id` null) and workspaces outside any collection belong to every view. Messages, Members and Settings are the group's and never narrowed.
    - A person is offered the collections they are in or that hold something they can open (owners/admins: all). The default is the remembered one, else the first they are in.
    - Opening a workspace from another collection (link, pin, notification) switches the view to it (`AppSidebar`).
    - It is a way of looking, not access: RLS decides what can be opened whatever is chosen. It adds no request (it reads the shell's cache entry); another group's collections appear in the menu only if that group was opened earlier in the tab.
  - Radix `Select` reports `''` when its options change under it; `AccessSelect` and `CollectionSelect` ignore that. Keep the guard.
  - `supabase/scripts/merge_groups.sql` is the one-time tool that folds one group into another as two collections (dry run unless `apply=1`). Moving a workspace between groups is otherwise unsupported; doc image access follows the doc id (`can_access_doc_image`), so a moved doc keeps its images.
- **Team tools vs workspace tabs:** Docs, Diagrams and Live exist at both levels as views of the same data. Rows have `team_id` (required) + `workspace_id` (nullable: null = team-wide; composite FK `(workspace_id, team_id) → workspaces(id, team_id)` keeps it in the same team). The team page shows everything the caller can access; the workspace tab shows only that workspace's rows. Docs, Diagrams and Live are built this way (`documents`/`diagrams`/`live_sessions`; Docs and Diagrams share the Files pages `TeamDocsPage`/`WorkspaceDocsPage`, Live has `TeamLivePage`/`WorkspaceLivePage`; one `DocPage`/`DiagramPage`/`LiveSessionPage` for both routes, `docLoader`/`diagramLoader`/`liveSessionLoader`). The "New …" dialog is the shared `CreateInScopeDialog` (Live uses its own `ScheduleSessionDialog`). Built workspace tools sit under `WorkspaceToolGate`, which 404s when the tool is off. Issues, Learning, Exercises and GitHub are workspace-only. **Resources was retired** (Docs with folders replaces it): the `'resources'` enum value remains in the database but is blocked by `workspace_modules_no_resources`, and `WorkspaceModule` excludes it.
- **Sidebar width:** the sidebar's right edge is a resize handle (`SidebarResizer`, a focusable `separator`): drag it, double-click to reset, or use the arrow keys (Shift = bigger steps, Home/End = the limits, Enter = reset). Limits and storage are in `lib/sidebar-width.ts` (178–448px, default 256; a narrow window caps the sidebar so the page keeps ~480px, without overwriting the saved choice); the choice is remembered in localStorage (`useSidebarWidth`) and applied through `--sidebar-width` on `SidebarProvider`. The width animation is switched off while dragging (inline `transition: none` on the sidebar container and gap). Collapsed to icons, the edge is the usual rail (click to expand); on mobile there is no handle.
- **Full-bleed pages:** the page area normally has padding and fills the full width, no limit (`PageArea`; the owner asked for this). A route with `handle: FULL_BLEED` (Messages, and diagram pages: a slim header row, then the editor filling the window; inside a workspace that also drops the workspace header and tabs), or the session page while a call is docked, switches it to full-bleed (`useFullBleed`): no padding or width limit, and the page sets its own height (`h-[calc(100svh-3rem)]`). `PageArea` and `WorkspaceLayout` keep the same elements and only change classes, because remounting the page would undock the call and flip the layout back and forth. A docked call has no frame; the floating one is the framed window.
- **Leaving or deleting** the current team or workspace: navigate away *first*, then invalidate (see `useExitTeam`). Otherwise the page crashes when its data disappears, or `/app` bounces back through the stale cache.
- **Deploys and open tabs:** a tab opened before a deploy can't load the new build's lazy chunks. `lib/stale-build.ts` reloads once (`vite:preloadError`, plus `RouteErrorPage` as a fallback), guarded against loops. Route errors never show raw error text.

## Naming (the original note)

> **Naming:** the UI calls a team a **group** ("Group settings", "Group-wide", "Create or join a group"). Code, routes (`/t/:teamSlug`), query keys and the database still say **team**. Keep new user-facing text on "group"; don't rename code for it. The same goes for issue **cycles**: the UI calls them **sprints** ("Sprint 3", "Current sprint", "New sprint"), while code, routes (`…/issues/cycles`), query keys, URL params (`?cycle=`), tables and docs below still say cycle. Keep new user-facing text on "sprint". Diagrams are called **Whiteboards** in the UI (owner's choice, 2026-10-25: a teacher's classroom board as much as a developer's schema board; "Board" was taken by the Issues view), with the `Presentation` icon, while code, routes (`…/diagrams/:id`, `?view=diagrams`), the `diagrams` table and tool, and query keys keep their names. Messaging is called **Chat** in the UI (sidebar item, page heading), while code, the route (`…/messages`), `features/messaging/`, tables and query keys keep their names; single messages are still "messages" ("New messages", "Load earlier messages"). The Ninety sync is called **EOS** in the UI (sidebar item, page title, Group settings section; owner, 2026-10-28), while code, the route (`…/ninety`), `features/ninety/`, the `ninety-sync` function, tables, the `ninety_sync` flag and query keys say ninety; "Ninety" stays in text only where it means the Ninety app itself. Docs and diagrams share one page the UI calls **Files** (sidebar item, workspace tab, `FILES_TAB` in `features/teams/nav.ts`), while code, routes (`…/docs`, item URLs `…/docs/:id` and `…/diagrams/:id`), tools (`workspace_modules` `docs` and `diagrams`, still two switches) and query keys keep their names; `…/diagrams` (the old list) redirects to `…/docs?view=diagrams`, or to `…/docs?folder=` when it named a folder (`DiagramsRedirect`).
