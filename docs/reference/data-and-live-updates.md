# Data loading, query keys and live updates

Read before adding a query, a loader, a table to Realtime, or anything that saves while someone types.

- **Data pattern:** `features/<name>/api.ts` exports `queryOptions` and mutation functions.
  - Loaders prime what the shell needs with `ensureQueryData`. Pages read with `useSuspenseQuery`; `AppLayout` has a Suspense boundary, so pages may also load secondary data that way.
  - Errors go through `lib/errors.ts` (`toDataError`, `requireAffected`), because RLS makes forbidden UPDATE/DELETE return 0 rows, not an error. Show them with `toast.error(errorMessage(e))`.
- **Shell data starts in loaders, never in a mounted component** (2026-10-27): the sidebar used to ask for workspace pins only after the workspace list arrived, and Starred, saved views, the bell and unread counts only after that, so a cold load took four rounds (~2.6 s throttled). `appLoader` now starts what needs only the user (profile, message preferences) and `teamLoader` starts the group's (Starred, views, unread counts, notifications) beside the awaited workspace list: two rounds. A new query the shell reads goes in one of those loaders. Pointing at the sidebar's Issues item prefetches the hub's data and its first tab's chunk (`prefetchIssues` in `AppSidebar`), and `NavigationSpinner` (in `AppLayout`) shows `DockSpinner` over the dimmed page while a loader takes over 150 ms (owner's choice: the custom spinner, not a bar).
- **Query keys:** `['teams', …]`, `['workspaces', …]`, `['documents', …]`, `['diagrams', …]`, `['issues', …]` (built by `issueKeys`) and `['repos', …]` (`repoKeys`); invalidate by prefix after mutations.
- **Live updates** (`lib/realtime.ts`, started by `useRealtimeSync` in `AppLayout`):
  - Supabase Realtime sends row changes (checked against RLS); the client invalidates the query prefixes in `AFFECTS`, by table name. A new table needs an entry there **and** a migration adding it to the `supabase_realtime` publication. `live_sessions`, `team_invites`, `profiles` and the GitHub install tables are left out on purpose.
  - Busy tables narrow what they refetch, using the event's row only to choose queries, never to show data:
    - `messages` (`messageQueries`): a new message refetches its conversation's timeline and the unread counts; a new reply only that conversation's threads.
    - `documents`, `diagrams`, `issues` (`rowQueries`): an update refetches the open item, and the lists only when a column they show differs from what is cached (`listsAlreadyShow`; it copies `updated_at` in). Saving text, a canvas or a description therefore costs other tabs nothing unless they have that item open.
  - **Own writes**: code that saves says so, keeps its own cache right, and its echo is dropped.
    - `ownSave(table, id)` is exact and is what editors and `useUpdateIssue` use: call it before the update, then call what it returns with the `updated_at` the save got back (`updateDocument`, `updateDiagram` and `updateIssue` return it). Only the event with that stamp is dropped, so someone else's change to the same row always gets through. Events for the row wait while the save is in flight.
    - `ownWrite(table, key)` drops by time (5 s), for rows whose stamp the tab can't know: a message it just sent (by id) and an issue's activity, branches and label links (by the issue's id). A mutation that uses it must refetch those itself.
    - A mutation that drops its echo must refetch whatever the server adds (`useUpdateIssue`: the detail and activity always, the list only on a status change).
  - Invalidation waits while a mutation is running, and everything is invalidated after a reconnect.
  - **Returning to the tab** refetches stale queries (60 s) only when live updates can't vouch for them: `lib/live.ts` (`keptLive`) is true while the realtime channel is subscribed and the key is under a published root. Keys no event refreshes are listed there (`NOT_LIVE`: invites, GitHub, signed URLs, search); add to it when a query under a live root reads a table that isn't published. Shell data that rarely changes (groups, members, the workspace list and roles, pins, saved views, message preferences, your profile) also uses `SETTLED_STALE_MS` (10 min, `lib/query-client.ts`).
  - Editors (issue description, docs, lessons, diagrams) keep a `synced` copy of what the server has: they take a changed server version only when nothing is unsaved (TipTap editors through `adoptContent` in `features/docs/editor/adopt.ts`), and after a save they cancel in-flight fetches of their own row before writing the cache. Keep both rules in any new editor. Edits aren't merged, so only one person edits a text at a time: `useOthersTyping` (Realtime Presence in `lib/presence.ts`; only people who can edit join; no API requests) returns `lockedBy`, the people who started typing first, and each editor is read-only with `OthersTypingAlert` while it isn't empty. The lock ends 8 s after their last edit (`TYPING_IDLE_MS`). Set it with `editor.setEditable(value, false)` so it isn't reported as an edit. It is a courtesy between browsers, not a database lock: a simultaneous start resolves to one person (earlier `since`, then tab id), but a tab without its presence connection isn't held back, and then it is last-write-wins as before.
  - `useCurrentTeam`/`useCurrentWorkspace` throw a 404-shaped error when the group or workspace disappears while open.
